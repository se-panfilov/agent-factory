# План исполнения Фазы 2

**Начать с `copilot-prompts/00-contract-and-foundation.md`.** Промпты выполняются по одному, после code review и merge предыдущего. Всего **16 заданий P00–P15**; это installer PR, не PR0–18 приложения из guide.

## Подготовка репозитория на доверенном ПК

Владелец создаёт приватный repo фабрики либо использует уже созданный. Помести этот комплект в `docs/automation/` с сохранением файлов/папки `copilot-prompts`. Передай Copilot полный текст выбранного prompt. Каждый ссылается на CONTRACT1.0.0 и содержит собственные ограничения. Source приложения, auth и state не копировать в docs. Copilot не должен помнить чат. Если в repo есть AGENTS.md, прочитать его и сохранить существующую структуру; конфликт контракта не разрешать произвольной заменой технологии.

M0 — обязательный внешний application milestone: reviewed package A1/A2/A3 с безопасным supervised runner и deployment-manifest. Если нет исходного проекта, сначала/параллельно вручную подготовить отдельный application PR0/1 по guide, а не поручать setup P06 создавать приложение. Installer P00–P15 можно реализовать и тестировать fake artifacts без M0, но end-to-end MVP qualification и реальное развёртывание до поставки M0 **заблокированы**. Это явная зависимость, а не скрытый последний шаг.

## Интеграционные контрольные точки

1. После P02 core contract/lock/gates/resume проходят fault fixtures; только затем разрешены host adapters.
2. После P05 disposable VM может проверить bootstrap→access→Docker, не модель и не app. Не ждать M1.
3. После P08 + M0 offline квалификация и owner live toy доступны. Это первый полезный installer milestone; P09+ не задерживают supervised запуск.
4. После P09 готов manual project+baseline путь. Никакого автоматического publisher обещания.
5. После P10/P11 + M1/M2 доступны service/backup/recovery; ни один missing capability не подменяется «успешным» systemd unit.
6. После P12/P13 проверяется opt-in isolated failure: cloud-only должен работать при отсутствии модели/платформ. Продуктовые PR остаются отдельными.
7. После P14/P15 получаются release archive, trusted keys/checksums, точный versions.lock и qualification report. P15 должен пройти также части P00–P08: не только последние advanced stages.

P01 до P15 использует только test fixture manifest; производственные fingerprints/версии заполняет и проверяет release stage. Bootstrap не скачивает package из ещё не созданного URL: release получается с ПК владельца и переносится по SSH. Самодостаточный archive с dist/deps снимает требование npm install installer на чистом сервере. Target app/npm dependency build остаётся отдельным S05 доверенным процессом.

Параллельное выполнение возможно только отдельной application командой над отдельным checkout/PR и без изменения setup interfaces. Для одного владельца рекомендуем строго последовательный маршрут. Не выдавать одновременно несколько installer prompts, меняющих package-lock/static registry/CONTRACT. Новая contract major требует повторного review downstream PR.

## Ограничения времени/доказательств

Не оценивать готовность числом написанных файлов. Каждый PR передаёт working tests, error fixtures, precise manual next steps и NOT RUN список. VM и реальные модели требуют отдельной среды/участия владельца. Нельзя обещать, что 16 Copilot prompts сами по себе реализуют orchestrator: они создают deployment pipeline для **существующего** release; недостающий продукт отмечен M0–M5.
